How it works

The measurement types, the UTM conversion and the Kalman core both filters share, and the simulator they run in.

getting startedhow it workssource on github

Both projects run in simulation: a drone in Cosys-AirSim, whose ROS 2 node publishes its GPS and IMU. Each project's simulation program adds sensor errors and turns the messages into the measurement types defined here, gps_fix and imu_sample, in metres in a flat frame. This repo also provides the filter core each project builds its estimator on. The maths comes from maintained libraries: GeographicLib for UTM, Eigen for the linear algebra.

measurements

  • gps_fix: time, position (utm), altitude, speed, true course and HDOP, what a receiver reports. The HDOP sets how far each fix is trusted (σ ≈ HDOP × UERE).
  • imu_sample: time, specific force in the sensor frame and the orientation (sensor to east/north/up), what an AHRS reports. acceleration_enu() rotates the force with Eigen's quaternion and subtracts g. At rest an accelerometer reads +g upward, which is why the subtraction is needed. Any error in g becomes a constant vertical bias, so the value is a parameter.

utm: degrees to metres

A filter wants a flat Cartesian frame. UTM splits the earth into 60 six-degree zones and projects each with a transverse Mercator. Within a zone, easting and northing are metres with a small, known scale error. utm converts with GeographicLib (UTMUPS, the standard zones including the Norway and Svalbard exceptions) and keeps the grid convergence: the angle between grid north and true north. Course and IMU headings are relative to true north, so the filters rotate them by the convergence before mixing them with UTM positions. The tests check the conversion against PROJ.

the filter core

kalman_filter<N> is the generic linear Kalman filter both projects use, on Eigen's fixed-size matrices (sizes checked at compile time, nothing allocated):

predict: x ← F x + u P ← F P Fᵀ + Q innovate: y = z − H x S = H P Hᵀ + R gate: NIS = yᵀ S⁻¹ y (χ² with dim z dof; reject above the 99.9 % value) update: K = P Hᵀ S⁻¹ x ← x + K y P ← (I − K H) P (I − K H)ᵀ + K R Kᵀ

S is at most 3 × 3, which Eigen inverts in closed form. The last line is the Joseph form. It costs a little more than (I − K H) P but keeps P symmetric and positive definite despite rounding. A filter that runs at 100 Hz for hours needs that.

threads and events

The simulation programs' ROS callbacks run one at a time on rclcpp's single threaded executor, so the filter they share needs no locks. tf2's listener spins on its own thread.

simulation helpers

  • airsim/: the simulator both projects run in, Cosys-AirSim on Unreal Engine 5.2 over ROS 2: the setup and run scripts, the AirSim settings of each scenario, the map generator, our patches to Cosys-AirSim and the launch file that starts AirSim's ROS 2 node, and autopilot.py, which flies the projects' figure eight over /cmd_vel so their programs only measure and estimate. airsim/README.md explains how a run works.
  • ros_sim.hpp: what the simulation programs (ROS 2 nodes for Cosys-AirSim) share: tf2 lookups in the enu frame (east, north, up on the ground at AirSim's origin; the truth is the TF enu → drone), and pose messages for the estimates, pointing along the estimated velocity. Their parameters are defined in YAML files and generated by generate_parameter_library.
  • Scoring is not here any more: the programs publish their estimates, the run is recorded, and airsim/evaluate.py scores the recording with evo (mean, RMS, median, p95, max). p95 is the error that 95 % of samples stay under: it shows the bad cases without being set by one outlier. See airsim/README.md.
